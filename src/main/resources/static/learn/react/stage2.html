阶段二

管理系统实战：把功能写成可维护页面

目标：能独立写一个常见后台模块，包括页面布局、工具栏、表格、表单、筛选、状态、接口预留。

1. 后台页面骨架

后台通常不是一个孤立页面，而是固定结构：侧边栏、顶部区域、内容区、表格区。

  • Sidebar：菜单和模块入口
  • main：当前业务页面
  • MetricCard：关键统计
  • Toolbar：搜索、筛选、批量操作

经验：后台系统最怕页面结构乱。先固定布局，再填功能，别一边写业务一边随手堆 HTML。

2. 数据流：谁拥有数据，谁负责改

当前练习里，AdminApp 保存用户数组，子组件通过 props 展示数据，通过回调通知父组件修改。

<UserForm onCreate={createUser} />
<UserTable users={filteredUsers} onRemove={removeUser} />

经验：先让页面顶层组件管理数据。等状态真的跨很多页面共享时，再考虑状态管理库。

3. 搜索和筛选

搜索词和筛选条件是状态，最终列表是计算结果。不要把筛选后的列表再单独存一份状态，容易不同步。

const filteredUsers = users.filter((user) => {
  return hitKeyword && hitStatus;
});

经验：能从已有数据算出来的值，优先计算，不要重复存。重复状态是很多 bug 的源头。

4. CRUD 操作

管理系统绕不开增删改查。现在练习里已经有新增、删除、状态切换，后续可以加编辑弹窗。

  • 新增：表单提交后 setUsers([user, ...users])
  • 删除：用 filter 去掉目标 ID
  • 修改：用 map 找到目标 ID 后替换

经验：修改数组时不要直接 push 或改原对象。React 更喜欢“给我一个新数组”。

5. 加载、空数据、错误

真实项目里，页面不只有“有数据”。你要设计四种状态：加载中、空数据、加载失败、正常数据。

  • loading：显示加载提示
  • error：显示失败原因和重试按钮
  • users.length === 0：显示空状态
  • 正常数据：显示表格

经验：商业项目的质感经常不在功能本身，而在这些边界状态有没有处理。

6. 接口预留思维

现在用本地数组，下一步可以替换成 Spring Boot 接口。页面结构不要依赖“假数据写死”。

async function loadUsers() {
  const response = await fetch("/restapi/users");
  const data = await response.json();
  setUsers(data);
}

经验：先定义前端需要的数据结构，再和后端对齐接口。不要让页面到处适配奇怪字段。
